1. Introduction

The Internet Programming Portal is a database-driven web application built with core PHP 8, MySQL (via PDO) and HTML5/CSS. Users register, log in, send Contact Us messages, and manage their submissions (search, sort, paginate, edit, delete, import/export CSV). Five protected pages (Dashboard, Profile, Contact Us, Submissions Directory, Information Hub) share a layout through PHP includes.

2. Database Design and ERD

Table summary

TablePurposeKey constraints / indexes
usersAccounts (hashed passwords, registration timestamp)PK id; UNIQUE username, email; INDEX created_at
user_profilesExtra profile details (1:1 with users)PK/FK user_id → users ON DELETE CASCADE
contact_submissionsContact Us messagesFK user_id → users (CASCADE); INDEX email, subject, created_at
activity_logAudit trail of login/CRUD eventsFK user_id → users (SET NULL); INDEX created_at

Normalisation: every table is in 3NF. Profile details are separated from credentials (users) to avoid null-heavy rows, and submissions reference the user by key instead of repeating account data. The subject labels are kept in a PHP multidimensional array and stored as text so the form can be changed without a migration; a lookup table could replace this later.

MySQL functions used: COUNT(), MAX(), NOW(), CONCAT(), COALESCE(), LIKE, CURRENT_TIMESTAMP. phpMyAdmin was used to create the database, import sql/schema.sql, inspect indexes/relations and export the final SQL file.

3.1 Sessions

On successful login the script calls session_regenerate_id(true) (prevents session fixation) and stores $_SESSION['user_id'] and $_SESSION['username']. Every protected page calls requireLogin(). Logout empties $_SESSION, expires the session cookie, calls session_destroy() and redirects to the login page.

3.2 Cookies

Two non-sensitive cookies are used: last_username (the “Remember my username” option on the login form, 30 days) and theme (light/dark preference set in the Information Hub). Both are HttpOnly and SameSite=Lax. Why sensitive data is never stored in cookies: cookies live on the user's device, are sent with every request, and can be read or edited by the user, malware, shared-computer users or (over plain HTTP) network attackers. Storing a password, password hash or user ID/role there would let an attacker impersonate the user. Only the session ID is kept in a cookie; all sensitive data stays on the server in $_SESSION and MySQL.

3.3 Database calls

All queries use PDO prepared statements with bound parameters. ORDER BY columns come from a whitelist, and LIMIT/OFFSET values are bound as integers.

3.4 Superglobals

$_POST (data-changing forms), $_GET (search, sort, page, string tools), $_SESSION (identity, CSRF token, flash), $_COOKIE (last username, theme), $_SERVER (request method, IP address, host, HTTPS flag), $_FILES (CSV import).

5. Installation Guide (local)

  1. Install XAMPP (or WAMP/Laragon); start Apache and MySQL.
  2. Copy the project folder into htdocs (e.g. C:\xampp\htdocs\ip_project).
  3. Open phpMyAdmin → Import → select sql/schema.sql → Go.
  4. Edit config/db.php if your MySQL credentials differ from root / empty password.
  5. Browse to http://localhost/ip_project/. Sample login: alice / Password123!.

6. GET vs POST in this Application

AspectGETPOST
Used forSearch/filter, sort, pagination, string tools, edit page (?id=)Register, login, profile update, contact form, edit/delete, CSV import, theme change
Data locationURL query stringRequest body
Side effectsNone (read-only, safe, idempotent)Changes data
Bookmark / shareYes – results can be bookmarked and refreshed safelyNo – and refresh warns about re-submission
PrivacyVisible in history, logs, referrer – never use for passwordsNot in URL; still needs HTTPS
Size limitsURL length limitsLarge bodies and file uploads
CSRFNot state-changingProtected by token

Justification: searching does not change data, so GET lets users bookmark and share filtered results and keeps the back button useful. Anything that creates, updates or deletes data, or carries credentials, uses POST with a CSRF token.

7. Framework Comparison

OptionAdvantagesDisadvantages
Core PHP + MySQL (chosen)No build tools; runs on any cheap/free host; teaches fundamentals (sessions, SQL, security); matches course scopeDevelopers must implement security, routing and structure themselves; more boilerplate; harder to scale
Laravel (PHP)Eloquent ORM, migrations, built-in auth, CSRF, validation, Blade; large ecosystemNeeds Composer/CLI and PHP 8+ hosting with public-folder control; steeper learning curve; hides fundamentals; heavier
Django (Python)“Batteries included”: ORM, admin panel, auth, security defaults; scalableNeeds Python hosting (WSGI) – rarely on free hosts; opinionated; more setup
Flask (Python)Lightweight, flexible, easy to learn, good for APIs/small appsMust pick/assemble extensions (auth, ORM, forms); Python hosting required; no built-in admin
Node.js (Express)One language front and back; non-blocking I/O; huge npm ecosystem; real-time (WebSockets)Needs a Node-capable host; callback/async complexity; unopinionated so structure varies; many third-party dependencies

Why core PHP: the assignment targets fundamentals; PHP/MySQL deploys directly to free shared hosting with phpMyAdmin; and writing validation, CSRF and prepared statements by hand demonstrates understanding that a framework would hide. For a production system with a larger team we would likely choose Laravel.
